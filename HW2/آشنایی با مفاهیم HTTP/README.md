۱. سوال اول

الف) مقایسه نسخه‌های مختلف HTTP به‌صورت کلیدواژه‌ای

HTTP/0.9:

تک‌منظوره (فقط دریافت متن HTML)

بدون Header و Status Code

فقط دارای متد GET

اتصال قطع‌شونده (Non-Persistent) پس از هر پاسخ

HTTP/1.0:

پشتیبانی از انواع MIME (ارسال عکس، فیلم و...)

اضافه شدن Headerها و Status Codeها

اضافه شدن متدهای POST و HEAD

اتصال جدید TCP برای هر در خواست/پاسخ (افت کارایی و Latency بالا)

HTTP/1.1:

اتصالات پایدار پیش‌فرض (Persistent Connections / Keep-Alive)

پشتیبانی از Pipelining (ارسال چند درخواست بدون انتظار برای پاسخ قبلی)

مکانیزم Chunked Transfer Encoding و هدر Host (پشتیبانی از Virtual Hosting)

مدیریت خطای Head-of-Line Blocking در لایه HTTP

HTTP/2:

پروتکل کاملاً باینری (Binary Protocol) به جای متنی

مالتی‌پلیسینگ (Multiplexing) واقعی (ارسال همزمان چند درخواست و پاسخ روی یک اتصال TCP)

فشرده‌سازی هدرها با الگوریتم HPACK

قابلیت Server Push برای ارسال پیش‌دستانه منابع به کلاینت

رفع مشکـل HOL Blocking در لایه HTTP (اما همچنان مبتلا در لایه TCP)

HTTP/3:

مبتنی بر پروتکل QUIC (روی لایه UDP) به جای TCP

حل کامل مشکل Head-of-Line Blocking در لایه انتقال (Transport Layer)

دست‌تکانی سریع‌تر (Zero-RTT / 1-RTT Handshake) و ترکیب TLS 1.3 با QUIC

پشتیبانی از Connection Migration (عدم قطعی ارتباط هنگام تغییر IP/شبکه کلاینت)

ب) دلیل استفاده از UDP در HTTP/3

پروتکل TCP دارای مکانیزم کنترل جریان و تحویل به ترتیب داده‌ها است. اگر یک پکت TCP در مسیر گم شود، تمام جریان‌ها (Streams) متوقف می‌شوند تا پکت مفقودشده دوباره ارسال شود (Head-of-Line Blocking در لایه Transport).

از آنجا که HTTP/2 چند جریان داده را روی یک اتصال TCP ارسال می‌کرد، افت حتی یک پکت TCP باعث مسدود شدن همه جریان‌ها می‌شد. برای حل این مشکل بنیادین، HTTP/3 از پروتکل UDP استفاده می‌کند و پروتکل جدیدی به نام QUIC را روی آن پیاده‌سازی می‌نماید. QUIC مکانیزم‌های قابلیت اطمینان (Reliability)، کنترل ازدحام و TLS را خودش به ازای هر جریان مستقل مدیریت می‌کند؛ در نتیجه مفقود شدن یک پکت UDP فقط همان جریان خاص را معطل می‌کند و سایر جریان‌ها بدون تاخیر دریافت می‌شوند.

۲. سوال دوم

الف) توضیح مفاهیم Stateful و Stateless

در معماری Stateless (بدون وضعیت)، هر درخواست کلاینت به سرور کاملاً مستقل است و سرور هیچ اطلاعاتی از نشست‌ها (Sessions) یا درخواست‌های قبلی کلاینت نگه نمی‌دارد؛ بنابراین هر درخواست باید شامل تمام اطلاعات لازم برای پردازش باشد. در مقابل، در معماری Stateful (با وضعیت)، سرور اطلاعات مربوط به وضعیت کاربر و سابقه تعاملات او را در حافظه خود ذخیره می‌کند و درخواست‌های بعدی وابسته به این داده‌های ذخیره‌شده پردازش می‌شوند.

ب) وضعیت HTTP و راهکار حل مشکلات آن

پروتکل HTTP ذاتاً یک پروتکل Stateless است. برای حل مشکل عدم ذخیره‌سازی وضعیت (که برای کاربردهایی مانند سبد خرید، لاگین ماندن و احراز هویت ضروری است)، از راهکارهای زیر استفاده می‌شود:

کوکی‌ها (Cookies): سرور با هدر Set-Cookie شناسه یا داده‌هایی را در مرورگر ذخیره می‌کند و کلاینت در درخواست‌های بعدی با هدر Cookie آن را بازمی‌گرداند.

نشست‌ها (Session IDs): سرور داده‌های کاربر را روی دیتابیس/حافظه خود نگه داشته و فقط یک شناسه یکتا (Session ID) به کلاینت می‌دهد.

توکن‌ها (مانند JWT): کلاینت توکن رمزنگاری‌شده حاوی وضعیت/هویت را ذخیره کرده و در هدر Authorization ارسال می‌کند.

۳. سوال سوم

الف) چالش مدل Client-Server در برنامه‌های تعاملی و real-time

در مدل سنتی HTTP، کلاینت همواره شروع‌کننده ارتباط است و سرور نمی‌تواند بدون درخواست کلاینت، داده‌ای برای او بفرستد. این ویژگی در کاربردهایی مثل چت، Alerting یا Webhookها چالش‌برانگیز است؛ زیرا اگر اتفاق جدیدی در سرور رخ دهد (مثلاً پیام جدیدی بیاید)، سرور راه مستقیمی برای آگاه‌سازی آنی کلاینت ندارد مگر اینکه کلاینت خودش بپرسد.

ب) راهکارهای ارائه شده برای حل این چالش

روش Short Polling:
کلاینت در فواصل زمانی مشخص و کوتاه (مثلاً هر ۳ ثانیه)، درخواست‌های HTTP متوالی به سرور ارسال می‌کند تا از وجود داده جدید مطلع شود. این روش باعث هدررفت شدید پهنای باند و منابع سرور (به دلیل هدرهای تکراری و پاسخ‌های خالی) می‌شود.

روش Long Polling:
کلاینت درخواست را می‌فرستد، اما سرور اتصال را باز نگه می‌دارد تا زمانی که داده جدیدی آماده شود (یا Timeout رخ دهد). پس از ارسال داده، اتصال بسته شده و کلاینت بلافاصله درخواست جدیدی ارسال می‌کند. این روش تاخیر را کاهش می‌دهد اما همچنان Over-head ایجاد ارتباط مجدد را دارد.

روش Server-Sent Events (SSE):
کلاینت یک اتصال پایداری ایجاد می‌کند و سرور داده‌ها را به صورت یک‌طرفه (از سرور به کلاینت) به شکل جریانی از متون (text/event-stream) ارسال می‌کند. این روش برای کاربردهایی مثل داشبوردهای زنده، اخبار و Alerting بسیار ایده‌آل و کم‌هزینه است.

پروتکل WebSocket:
یک ارتباط دوطرفه (Full-Duplex)، پایدار و مبتنی بر سوکت روی یک اتصال TCP ایجاد می‌کند. ارتباط با یک دست‌تکانی HTTP (Upgrade Header) شروع شده و سپس به پروتکل WebSocket سوییچ می‌کند. هر دو طرف می‌توانند در هر لحظه با حداقل Overhead داده بفرستند که بهترین گزینه برای سیستم‌های چت و بازی‌های آنلاین است.

پروتکل WebTransport (در HTTP/3):
راهکار مدرن مبتنی بر QUIC/UDP که امکان ارسال جریان‌های دوطرفه و یک‌طرفه را با تاخیر فوق‌العاده پایین و بدون مشکل Head-of-Line Blocking فراهم می‌کند.

۵. سوال پنجم

پاسخ و کدهای وضعیت HTTP (Status Codes) مناسب برای REST API:

۱. دیتابیس وبسایت مشکل پیدا کرده و درخواست لاگین انجام نمی‌شود:

کد مناسب: 500 Internal Server Error (یا 503 Service Unavailable)

دلیل: خطای سمت سرور و عدم توانایی سیستم در پردازش درخواست به دلیل خرابی دیتابیس.

۲. نام کاربری واردشده داخل سایت وجود ندارد و لاگین ناموفق بوده است:

کد مناسب: 401 Unauthorized (یا 404 Not Found / 400 Bad Request)

دلیل: در مسائل احراز هویت، 401 Unauthorized استانداردترین کد برای عدم موفقیت در لاگین است. (نکته امنیتی: بهتر است جهت جلوگیری از User Enumeration، پیام کلی «اعتبارنامه‌ها نامعتبر است» داده شود).

۳. وبسایت به دامنه دیگری منتقل شده است:

کد مناسب: 301 Moved Permanently (یا 308 Permanent Redirect)

دلیل: انتقال دائمی آدرس منبع به یک URL جدید.

۴. تعداد درخواست‌های ارسال‌شده از طرف کاربر از نرخ مجاز بیشتر است:

کد مناسب: 429 Too Many Requests

دلیل: تجاوز کلاینت از محدودیت نرخ ارسال درخواست (Rate Limiting).

۵. درخواست تمدید توکن (JWT) موفقیت‌آمیز بوده و توکن جدید در هدر بازگردانده شده:

کد مناسب: 200 OK (یا 204 No Content اگر بدنه خالی باشد)

دلیل: درخواست با موفقیت پردازش شده و پاسخ/هدرهای جدید به کلاینت تحویل داده شده است.

۶. کاربر از رنج IP ممنوعه (تحریم/بلاک) برای دسترسی به سرویس استفاده می‌کند:

کد مناسب: 403 Forbidden (یا 451 Unavailable For Legal Reasons)

دلیل: سرور درخواست را فهمیده اما اجازه دسترسی به این IP/کاربر را نمی‌دهد. کد ۴۵۱ نیز در صورت وجود محدودیت‌های قانونی و تحریمی گزینه‌ای بسیار دقیق است.

۶. سوال ششم

تعیین نوع پروکسی برای هر سناریو:

۱. استفاده از سرورهای داخلی دانشگاه به جای سرورهای مرکزی برای دریافت پکیج‌ها (مانند apt):

نوع پروکسی: Forward Proxy (از نوع caching/mirror proxy)

دلیل: درخواست‌های کلاینت‌های داخلی را گرفته و به عنوان نماینده آن‌ها از سرور مقصد دریافت می‌کند و برای کاهش پهنای باند کَش می‌نماید.

۲. تقسیم درخواست‌ها بر اساس مبدأ جغرافیایی درخواست‌ها:

نوع پروکسی: Reverse Proxy (با قابلیت Geo-routing / Load Balancer)

دلیل: جلوی سرورهای اصلی قرار می‌گیرد، درخواست‌های ورودی کلاینت‌ها را دریافت کرده و به سرور مناسب هدایت می‌کند.

۳. اضافه کردن قابلیت احراز هویت برای یک سرویس بسیار قدیمی:

نوع پروکسی: Reverse Proxy (یا Authentication Gateway / Sidecar Proxy)

دلیل: بدون دستکاری کدهای سرویس قدیمی، پروکسی جلوی آن قرار گرفته، درخواست‌ها را احراز هویت کرده و سپس به سرویس اصلی پاس می‌دهد.
