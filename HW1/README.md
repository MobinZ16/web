## ۱. سؤال اول: merge و rebase

### ۱.۱. توضیح عملکرد دستورها

- **دستور `git merge`:** دو شاخه را با ایجاد یک «کامیت ادغام» (Merge Commit) جدید به هم وصل می‌کند. این دستور تاریخچه انشعابات را کاملاً حفظ کرده و ساختار واقعی شاخه‌ها را دست‌نخورده باقی می‌گذارد.
- **دستور `git rebase`:** تغییرات (کامیت‌های) شاخه فعلی را موقتاً برداشته و آن‌ها را روی سرِ شاخه مقصد (Base جدید) مجدداً اعمال (Replay) می‌کند. در نتیجه، تاریخچه کامیت‌ها به صورت خطی (Linear) درمی‌آید، انگار که تمام تغییرات از ابتدا روی همان شاخه اصلی توسعه یافته‌اند.

### ۱.۲. تفاوت‌ها از نظر ترکیب تغییرات و شکل تاریخچه

- **نحوه ترکیب:** در روش `merge` یک کامیت جدید با دو والد (Parent) ساخته می‌شود، در حالی که در `rebase` کامیت‌های قبلی بازنویسی شده و کامیت‌هایی جدید با شناسه (Hash) تازه ایجاد می‌شوند.
- **شکل تاریخچه:** تاریخچه حاصل از `merge` به‌صورت ساختار شبکه‌ای و دارای انشعاب است (حفظ تاریخچه واقعی کار گروهی)، اما در `rebase` تاریخچه‌ای کاملاً خطی، یکدست و بدون شاخه‌های موازی حاصل می‌شود.

### ۱.۳. موقعیت‌های مناسب استفاده و دلایل آن

- **موقعیت مناسب `merge`:** ادغام شاخه‌های اصلی و عمومی پروژه (مانند ادغام شاخه توسعه یا فچر به شاخه `main`).
  - _دلیل انتخاب:_ در شاخه‌های عمومی نباید تاریخچه کامیت‌ها بازنویسی شود؛ زیرا هم‌تیمی‌ها کدهای این شاخه را دریافت کرده‌اند. استفاده از `merge` تمام سوابق و تاریخ واقعی توسعه را دقیقاً حفظ می‌کند.
- **موقعیت مناسب `rebase`:** به‌روزرسانی یک شاخه شخصی (Feature Branch) با آخرین تغییرات شاخه اصلی (`main`) قبل از ادغام نهایی.
  - _دلیل انتخاب:_ این کار باعث می‌شود تاریخچه کامیت‌های محلی تمیز مانده، کامیت‌های تکراری و غیرضروری حذف شده و بررسی کدها (Code Review) توسط سایر اعضا آسان‌تر شود.

## ۲. سؤال دوم: انتخاب بخشی از تغییرات (Interactive Staging)

### ۲.۱. مفهوم Hunk در خروجی diff

در خروجی مقایسه تغییرات (`git diff`)، به هر قطعه یا بلوک از تغییرات متوالی (شامل خطوط اضافه، حذف یا ویرایش شده به همراه چند خط زمینه یا Context پیرامون آن) یک **Hunk** گفته می‌شود.

### ۲.۲. بررسی تعاملی و افزودن گزینشی تغییرات

برای بررسی تعاملی تغییرات و قرار دادن گزینشی آن‌ها در ناحیه staging، از دستور زیر استفاده می‌شود:

```bash
git add -p
# یا
git add --patch
```

با اجرای این دستور، گیت تغییرات فایل را به‌صورت Hunk به Hunk نمایش داده و کلیدهای تعاملی زیر را در اختیار می‌گذارد:

- `y` (yes): اضافه کردن Hunk فعلی به ناحیه staging.
- `n` (no): رد کردن Hunk فعلی (عدم اضافه به staging).
- `s` (split): تقسیم Hunk فعلی به Hunkهای کوچک‌تر (در صورت وجود خطوط تغییرنیافته در میان آن‌ها).
- `e` (edit): ویرایش دستی Hunk در محیط ویرایشگر متنی.
- `q` (quit): خروج از وضعیت تعاملی.

### ۲.۳. فایده برای ساختن کامیت‌های منسجم (Atomic Commits)

گاهی روی یک فایل، تغییراتی مربوط به دو موضوع متفاوت (مثلاً رفع یک باگ و افزودن یک ویژگی جدید) انجام می‌شود. با این روش می‌توان تغییرات مربوط به باگ را جداگانه Staged و کامیت کرد و سپس تغییرات ویژگی جدید را در کامیت دیگری قرار داد. این امر باعث ایجاد کامیت‌های منسجم، کوچک و هدفمند می‌شود که اشکال‌زدایی و بازگردانی آن‌ها در آینده بسیار ساده‌تر خواهد بود.

## ۳. سؤال سوم: یافتن منشأ خطا با `git bisect`

### ۳.۱. نحوه کار دستور

دستور `git bisect` از الگوریتم **جستجوی دودویی (Binary Search)** روی تاریخچه کامیت‌ها استفاده می‌کند تا عیب یا باگ وارد شده به پروژه را در کمترین زمان ممکن پیدا کند.

### ۳.۲. مراحل پیدا کردن کامیت معیوب

1. **شروع فرایند:**
   ```bash
   git bisect start
   ```
2. **مشخص کردن کامیت معیوب (Bad Commit):** معمولاً کامیت فعلی که خطا در آن دیده می‌شود.
   ```bash
   git bisect bad
   ```
3. **مشخص کردن کامیت سالم (Good Commit):** یک شناسه کامیت قدیمی‌تر که مطمئن هستیم خطا در آن وجود نداشته است.
   ```bash
   git bisect good c1a2b3c
   ```
4. **تست و ارزیابی تکرارشونده:** گیت به‌صورت خودکار به کامیت میانی این بازه می‌رود (`HEAD` تغییر می‌کند). پروژه را تست کرده و اعلام می‌کنیم:
   - اگر خطا وجود داشت: `git bisect bad`
   - اگر خطا وجود نداشت: `git bisect good`
5. **شناسایی کامیت خطاکار:** گیت این روند را تکرار می‌کند تا دقیقاً اولین کامیتی را که خطای مذکور را وارد کرده، مشخص و گزارش کند.
6. **پایان جستجو و بازگشت به حالت اولیه:**
   ```bash
   git bisect reset
   ```

### ۳.۳. مثال کاربردی و دلیل مفید بودن

- **مثال:** در یک پروژه با ۱۰۰ کامیت جدید، برنامه‌نویس متوجه می‌شود فرم ورود کاربران کار نمی‌کند. با مشخص کردن کامیت ۱ (سالم) و کامیت ۱۰۰ (خراب)، گیت ابتدا کامیت ۵۰ را بررسی می‌کند. اگر سالم بود، بازه به ۵۰ تا ۱۰۰ محدود می‌شود و این فرایند ادامه می‌یابد.
- **دلیل مفید بودن:** به جای بررسی تک‌تک ۱۰۰ کامیت (که بسیار زمان‌بر است)، با استفاده از پیچیدگی زمان $O(\log n)$، کلاً با ۷ بار تست کردن می‌توان کامیت مخرب را پیدا کرد.

## ۴. سؤال چهارم: بررسی تغییرات پیش از کامیت

### ۴.۱. دستورهای بررسی وضعیت و تفاوت دو دسته تغییرات

- **بررسی تغییرات Unstaged (ثبت‌نشده در staging):**
  ```bash
  git diff README.md
  ```
- **بررسی تغییرات Staged (آماده کامیت):**
  ```bash
  git diff --staged README.md
  # یا
  git diff --cached README.md
  ```
- **تفاوت دو دسته تغییرات:**
  - تغییرات Staged شامل مواردی است که قبل از ویرایش دوم با `git add` علامت‌گذاری شده‌اند و آماده ثبت هستند.
  - تغییرات Unstaged شامل ویرایش‌های جدیدی است که **بعد** از دستور `git add` روی فایل اعمال شده‌اند و هنوز گیت آن‌ها را برای کامیت بعدی در نظر نگرفته است.

### ۴.۲. ثبت کامیت معمولی بدون گزینه `-a`

اگر در این وضعیت دستور `git commit -m "update README"` را اجرا کنیم:

- **تغییرات ثبت‌شده:** فقط تغییراتی که **قبل** از ویرایش مجدد در ناحیه staging قرار گرفته بودند در کامیت جدید ثبت می‌شوند.
- **تغییرات باقی‌مانده:** ویرایش‌های انجام‌شده **بعد** از اجرای دستور `git add` همچنان در Working Tree به‌صورت Unstaged باقی می‌مانند.
- **دلیل:** گیت موقع ثبت کامیت، snapshot موجود در ناحیه Staging را ذخیره می‌کند، نه وضعیت فعلی فایل روی دیسک را.

### ۴.۳. جلوگیری از اضافه شدن پوشه `tmp`

- **تنظیمات لازم:** باید فایلی به نام `.gitignore` در ریشه مخزن ایجاد (یا ویرایش) کرده و مسیر پوشه را به آن اضافه کنیم:
  ```gitignore
  tmp/
  ```
- **آیا برای فایل tracked کافی است؟** خیر. اگر فایلی قبلاً tracked شده باشد، افزودن نام آن به `.gitignore` مانع از پیگیری تغییراتش نمی‌شود. برای فایل‌های tracked شده باید ابتدا آن‌ها را با دستور زیر از مدیریت گیت خارج کرد و سپس به `.gitignore` افزود:
  ```bash
  git rm --cached <file-path>
  ```

## ۵. سؤال پنجم: رفع merge conflict در کار گروهی

### ۵.۱. علت وقوع Conflict

- **علت:** Conflict زمانی رخ می‌دهد که دو شاخه متفاوت، **دقیقاً یک خط یا یک بخش مشترک** از یک فایل را به مقادیر متفاوتی تغییر داده باشند و گیت نتواند تشخیص دهد کدام نسخه باید اولویت داشته باشد.
- **آیا هر تغییری باعث conflict می‌شود؟** خیر. اگر دو نفر روی فایل‌های متفاوت یا حتی بخش‌ها و خطوط متفاوتی از یک فایل کار کرده باشند، گیت به‌صورت خودکار تغییرات را ترکیب (Auto-merge) می‌کند.

### ۵.۲. شناسایی فایل‌های دارای Conflict و نقش نشانگرها

برای شناسایی فایل‌های دچار مشکل از دستور زیر استفاده می‌شود:

```bash
git status
```

فایل‌های دارای تعارض با عبارت `both modified` مشخص می‌شوند.

با باز کردن فایل، نشانگرهای تعارض (Conflict Markers) به شکل زیر دیده می‌شوند:

```markdown
<<<<<<< HEAD
متن تغییر یافته در شاخه فعلی (main)
=======
متن تغییر یافته در شاخه در حال ادغام (feature-description)

> > > > > > > feature-description
```

- `<<<<<<< HEAD` تا `=======`: نشان‌دهنده تغییرات شاخه مقصد (محلی).
- `=======` تا `>>>>>>>`: نشان‌دهنده تغییرات شاخه مبدا (در حال ادغام).

### ۵.۳. مراحل رفع conflict و حفظ هر دو تغییر

1. فایل `README.md` را در ویرایشگر باز کرده و متن نهایی را به‌گونه‌ای ترکیب می‌کنیم که اطلاعات هر دو تغییر حفظ شود.
2. تمام علامت‌های `<<<<<<<`، `=======` و `>>>>>>>` را به‌طور کامل پاک می‌کنیم.
3. فایل اصلاح‌شده را به ناحیه staging اضافه می‌کنیم:
   ```bash
   git add README.md
   ```
4. با ثبت کامیت، عملیات ادغام را به پایان می‌رسانیم:
   ```bash
   git commit
   ```

- **اطمینان از عدم بقای نشانگرها:** با جستجوی متنی عبارت `<<<<<<<` در فایل یا اجرای `git diff` قبل از کامیت مطمئن می‌شویم هیچ نشانگری باقی نمانده است.

### ۵.۴. لغو عملیات Merge

اگر تصمیم بگیریم فعلاً ادغام انجام نشود، با دستور زیر عملیات را لغو کرده و مخزن را به وضعیت پاک قبل از merge بازمی‌گردانیم:

```bash
git merge --abort
```

## ۶. سؤال ششم: انتخاب روش مناسب برای بازگرداندن تغییرات

### ۶.۱. حذف تغییرات Unstaged در فایل `notes.txt`

- **دستور:**
  ```bash
  git restore notes.txt
  ```
- **توضیح و اثرات:** این دستور تغییرات محلی موجود در Working Tree برای فایل `notes.txt` را پاک کرده و فایل را به آخرین وضعیت Staged/Committed بازمی‌گرداند. سایر فایل‌ها دست‌نخورده می‌مانند و هیچ تغییری در تاریخچه کامیت‌ها ایجاد نمی‌شود.

### ۶.۲. خروج فایل از Staging بدون پاک شدن ویرایش‌ها

- **دستور:**
  ```bash
  git restore --staged notes.txt
  ```
- **توضیح و اثرات:** این دستور وضعیت فایل را از Staged به Unstaged تغییر می‌دهد. تغییرات و ویرایش‌های انجام‌شده روی فایل در Working Tree کاملاً حفظ می‌شوند. ناحیه Staging به‌روز شده و تاریخچه کامیت‌ها تغییری نمیکند.

### ۶.۳. بازگرداندن کامیت پوش‌شده روی شاخه مشترک `main`

- **دستور و روش مناسب:**
  ```bash
  git revert <commit-hash>
  ```
- **توضیح و اثرات:** این دستور یک کامیت جدید (Revert Commit) ایجاد می‌کند که دقیقاً عکس تغییرات کامیت اشتباه را روی کد اعمال می‌کند. Working Tree و Staging پاک شده و آماده Push کردن این کامیت جدید می‌شوند.
- **دلیل عدم استفاده از حذف کامیت و Force Push:**
  از آنجا که این کامیت روی شاخه عمومی `main` قرار گرفته و سایر هم‌تیمی‌ها آن را دریافت کرده‌اند، بازنویسی تاریخچه با `git reset` و `git push --force` باعث ناهمخوان شدن تاریخچه مخزن سایر اعضا می‌شود. این کار ریسک از بین رفتن کدهای دیگران و ایجاد conflictهای پیچیده را بسیار بالا می‌برد. دستور `revert` با اضافه کردن یک کامیت جبرانی، تاریخچه را بدون تخریب بازنویسی حفظ می‌کند.
